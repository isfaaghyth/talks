you ask for the code
you re-paste the requirements
you apply the patch, fix errors
you rebuild, it's still red

The agent is the loop.
you message the bot: "build a counterapp"
agent scaffolds the project, builds it
agent reads build errors, fixes itself
agent ships the APK back to the chat
you review the code before merge the PR
You reappear once, to install the APK.
04 / 19 THE ENGINEERING INSTANCE

🦉 pang — An agentic workflow for engineering loops

A self-hosted, agentic software-engineering system. You describe a project in a note; an engineer agent picks it up, confirms the platform with you over Telegram, scaffolds a real codebase, and builds it. It runs alongside a personal ghiath assistant and shares nothing with it but the LLM gateway.

Orchestrator

hermes-agent

A long-lived engineer agent that spawns per-project eng-<name> build agents.

Cognitive core

Obsidian vault

Plain Markdown — projects, decisions, task logs. Vendor-agnostic, synced to every device.

LLM gateway

KeiRouter

The one place provider keys live. Swap models in one spot; agents never hold keys.

05 / 20 HOW IT WORKS

Obsidian vault observable for tasks, no webhook

There is no webhook. hermes agents have no HTTP endpoint — their gateway is a Telegram poller. So the trigger is a frontmatter field in a Markdown note, watched by a cron tick.

~/ippang/vault-project/timerapp/00-context.md 
---
project: timerapp
instance: ippang            # never 'ghiath' — tags the note
platform: mobile          # web | mobile | backend
status: backlog           # -> in-progress FIRES provisioning
created: 2026-07-30T09:12:00+0700
---
edit status → in-progress → cron tick (60s) → hermes -p engineer -z → confirm over Telegram

The tick is debounced by a state file, so editing the note body never re-fires — only a backlog → in-progress transition does. The engineer then confirms the platform and delegates the build to an isolated eng-timerapp agent.

06 / 20 THE TRIGGER

Engineering Loops with project-tick

Registered with hermes cron in --no-agent mode: the script itself decides whether to spawn, and its stdout is delivered to Telegram.

_instance/hermes-cron/project-tick.py 
# runs every minute: hermes cron '* * * * *' --no-agent \
#   --script project-tick.py --deliver telegram --name ippang-projects

for note in vault.glob("*/00-context.md"):
    fm = parse_fm(note.read_text())["fm"]

    if fm["instance"] != "ippang":   # isolation guard
        continue

    # 1. ingestion: backlog -> in-progress fires the engineer
    if fm["status"] == "in-progress" and not already_dispatched:
        spawn("engineer", brief)      # hermes -p engineer -z ...

    # 2. reporting: a terminal status -> one line to Telegram
    if fm["status"] in TERMINAL:
        print(f"[{project}] {status}")  # stdout -> chat
cron logic · click to step
01 scan vault for */00-context.md every 60s
02 guard: instance == "ippang"? else skip
03 status backlog → in-progress → spawn engineer
04 terminal status → print → delivered to Telegram
05 3 failed spawns → note flagged status: error
07 / 20 THE ENGINEER AGENT

One orchestrator, many builders

The engineer profile is long-lived. Its SOUL.md is plain prose: read the note, confirm the platform over Telegram, then provision and delegate. The real coding is done by fresh, scoped eng-<name> agents — one per build.

orchestrator → builders · click to spawn
engineer orchestrator
eng-timerapp android
eng-counterapp android + click to spawn tester
eng-counterapp-tester qa engineer
scoped to counterapp's vault subtree — reads the app's memory to plan & assert coverage
eng-notesapp web
+ as many eng-<name> as the current builds need — each scoped to its own dir & vault subtree, isolated from the others

    --i-confirm-mobile-cost

# 3. delegate the build to the scoped project agent

# 4. keep the note's status truthful as you go

08 / 20 WHY SUBAGENT MATTERS

Subagents are the scoped workforce

A subagent is a child session spawned by a parent agent to do one bounded job — keeping the main context lean and the role crisp.

🧩 Role separation Unlike primary agents (like Build or Plan), subagents run in restricted or specialized child sessions — each with its own role, scope, and memory.
🧰 Built-in options Includes general for multi-step tasks, explore for read-only codebase searches, and scout for checking external dependencies.
🪶 Context efficiency Prevents main context pollution and lowers token usage by isolating heavy lookups or research into throwaway child sessions.

10 / 20 COGNITIVE CORE

Why retain a cognitive core

↺ what the agent learns is written back to Obsidian, re-indexed, and recalled next time — the loop compounds.

Why Obsidian

Plain Markdown on disk — readable by humans and agents, owned by you, no SaaS lock-in. The agent reads and writes it directly as memory.

Why CouchDB

LiveSync replicates the vault to every device over your own server — a note edited on the phone reaches the agent, conflict-tolerant, instantly.

Why Qdrant

Embeds every note into a vector index, so the agent recalls by meaning, not keywords — context that scales as the vault grows.

12 / 20 DESIGN COLLABORATION

Google Stitch — the design before the code

Before the agent writes a line of Kotlin, Google Stitch generates the skeleton design — screens, layout, and a basic design system (colors, type, spacing). The engineer feeds that into the scaffold, so the Compose UI is grounded in a real design, not a guess.

Google Stitch → skeleton screens → design system (tokens) → engineer scaffold → Compose UI
What Stitch gives

Skeleton + design system

Screen layouts and a basic token set — colors, typography, spacing — the visual contract the build agent codes against.

What the agent does

Scaffold to match

The android-dev skill consumes the Stitch output and emits Compose theme + screens, so design and code stay in lockstep.

A nod to today's host — built with Stitch in mind, and demoed live from the Google office.

Stand up the whole stack on your Mac and run the loop end-to-end before touching a server. One idempotent script brings up CouchDB, Qdrant, n8n, ntfy, keirouter, the LiveSync bridge, the indexer, and configures the engineer profile.

20 / 20 CONCLUSION

The workflow is the product, not the prompt

  • An agent alone is just a smarter autocomplete — the loop is what makes it useful.
  • A note's status field, a cron tick, and a long-lived orchestrator turn one-off prompting into a repeatable system.
  • Scope each build to its own agent and vault subtree — fast loops, contained mistakes.
  • Start small: one note, one engineer, one APK — then let the pipeline grow.
